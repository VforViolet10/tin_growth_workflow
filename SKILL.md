# Community Question Radar

## Goal
Produce a small, founder-actionable list of public conversations where a real buyer is
already discussing a problem the product can help solve. The unit of work is a conversation,
not a channel or a content theme.

## 1. Load the company's context
Read the existing onboarding plan, feature map, code/product map, writing style when present,
and useful outputs from earlier runs. Identify:
- the primary buyer and their job/problem;
- 3-5 concrete problems or questions the product solves;
- claims the company is actually allowed to make;
- any hard "no" constraints.

Never invent a capability or proof point. If the project context is too thin to establish
product fit, say so and stop rather than guessing.

## 2. Turn problems into search hooks
Convert each problem into natural phrases a buyer might type into a public community. Mix:
- problem questions ("how do I...", "struggling with...");
- comparison/trade-off questions;
- implementation questions;
- "what are people using for..." questions.

Prefer the buyer's language over product/category jargon.

## 3. Search public conversations
Use the available web/browser capability to inspect public, indexable discussions. Search
across several plausible communities rather than assuming one platform. Look for places such
as Reddit, Hacker News, public forums, specialist communities, public Q&A pages, and public
discussion threads.

For every candidate, capture:
- exact public URL;
- community/site;
- approximate date if visible;
- the question/problem being discussed;
- evidence that the author is the target buyer or has the target problem;
- whether replies are still possible/relevant.

Do not use private groups, login-only pages, scraped personal data, or pages whose contents
cannot be verified.

## 4. Score before drafting
Score each candidate from 0-2 on four dimensions:
- Intent: how close the conversation is to a problem that can lead to the product category.
- Fit: how directly the company's actual product solves the stated problem.
- Freshness: whether the conversation is recent or still actively receiving responses.
- Helpfulness: whether the company can add a genuinely useful answer without forcing a pitch.

Keep only candidates scoring at least 6/8. Break ties by choosing the conversation where the
answer can stand alone as useful advice even if the reader never buys.

Reject:
- generic "tell me about your product" threads;
- spam/SEO threads;
- closed or archived discussions where posting is not practical;
- questions the product cannot answer;
- conversations that require pretending to be a customer;
- opportunities where the only useful response would be an advertisement.

## 5. Draft the reply
For each selected conversation, write a 60-120 word reply:
1. answer the person's actual question first;
2. give one concrete step, example, or trade-off;
3. mention the company's product only if it naturally belongs in the answer;
4. never fabricate proof, customers, benchmarks, or personal experience.

If a product mention would make the response promotional, write a no-pitch answer instead and
mark the product mention as optional.

## 6. Produce the founder handoff
Write reports/COMMUNITY_QUESTION_RADAR.md with:
- Run date and search scope.
- A short "what changed" or "why now" section.
- A table of selected opportunities with: priority, community, question, URL, score, and why it
  is worth answering.
- For each opportunity: evidence, reply draft, optional product mention, and posting caution.
- A "First 3 actions" section telling the founder exactly which conversations to open first and
  what to do.
- A "Rejected near-misses" section with 2-4 examples when useful, so the founder can see the
  quality bar.
- A limitations section covering inaccessible, stale, or ambiguous evidence.

The final output is a decision-ready posting queue. It is not permission to publish anything.
Never send, post, comment, upvote, follow, or contact anyone.
